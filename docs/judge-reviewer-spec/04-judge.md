> **Audience**: Builders of research-artifact evaluation tools.
> **Source of truth for**: The judge's finding model, checks, validator catalog semantics,
> contribution diagnostics, aggregation into a rubric and badges, advisory overlays, and the
> reproduction hook.

# 4. Judge

The judge evaluates the **artifact**. Its core is deterministic (I2). It answers: *is the
evidence the artifact ships present, intact, consistent with its claims and its paper, and (if a
reproduction provider exists) reproducible?* It never judges novelty, significance, or whether
the paper should be accepted.

## 4.1 Verdict vocabularies

**Verdict** (every finding has exactly one):

| Value | Meaning |
|-------|---------|
| `verified` | Evidence supports the requirement or claim. |
| `failed` | Contradicted, or a required element is missing. The only verdict that can produce `NOT_REPRODUCED`. |
| `unverifiable` | Declared but cannot be resolved or settled with what is shipped. Visible; blocks `REPRODUCED`; not a failure. |
| `unassessable` | The evidence this check needs was never declared. A coverage note, excluded from aggregation. |
| `advisory` | An observation. Never affects the rubric **unless** the finding also carries a mode verdict (e.g. an `attest` pass, `attested`); mode-keyed findings are aggregated by their mode verdict (§4.7). |

**Validation mode** (SDK §3.1): `re-execute`, `re-analyze`, `inspect`, `attest`.

**Mode verdict** (set only on claim-level findings that took part in the mode-keyed model):

| Value | Tier | Earned when |
|-------|------|-------------|
| `re-executed` | reproduction | A validator passed against outputs the **tool itself** regenerated by re-running pinned code (requires a reproduction provider, §4.9). |
| `re-analyzed` | reproduction | A validator passed against numbers the **tool itself** recomputed from released data (requires a reproduction provider). |
| `evidence-supported` | capped | A validator passed against the **producer's shipped** evidence. |
| `attested` | capped | An `attest` validator that is the claim's own validator passed. |
| `unverifiable` | — | Could not be settled. |
| `unassessable` | — | Not declared. |
| `failed` | — | A validator ran and its condition was false. |

Producer-declared `validation_mode` is recorded on the finding but MUST NOT raise the mode
verdict (I7). Checking a producer's shipped output is `evidence-supported`, whatever mode the
producer declared.

**Presentation role** (display only; MUST NOT influence any verdict): `holds_up`,
`needs_attention`, `coverage`. A RECOMMENDED default: `verified` or positive mode verdicts →
`holds_up`; `failed`, `unverifiable` → `needs_attention`; `unassessable` → `coverage`;
`advisory` → the check decides.

## 4.2 Finding

```json
{
  "id": "claim_validators/C1.v0",
  "check": "claim_validators",
  "verdict": "verified",
  "message": "claim C1: numeric_close 0.912 ≈ 0.91 (rel_tol=0.01) — passed.",
  "evidence": ["claims.yml#C1", "results.yml#R3", "evidence/metrics.csv"],
  "command_to_reproduce": "<a command or instruction that re-derives this finding>",
  "grounded_in": "S1, S3",
  "validation_mode": "re-analyze",
  "mode_verdict": "evidence-supported",
  "method_badge": "inspected",
  "display_weight": null,
  "presentation_role": "holds_up",
  "display": {}
}
```

| Field | Rule |
|-------|------|
| `id` | `<check>/<subject>`. Stable across runs for the same artifact. Unique within a result. |
| `check` | Name of the producing check: always one of `structure`, `claim_validators`, `paper_consistency`, `provenance`, `assessments`, `reproduce` (or a custom check's name, §7.5). Assessment dimensions appear only in the `id`. |
| `message` | One human-readable sentence or two. MUST state the cause of any non-`verified` verdict. Wording is free except for phrases this specification puts in double quotes as "MUST contain"; those are tested verbatim, case-insensitively. Any other quoted text, including quotes inside condition tables, is example wording. |
| `evidence` | Anchors a reader can open: artifact-relative paths, or `<file>#<id>` anchors such as `claims.yml#C1`, `SHA256SUMS#L4`, `manifest.yml#evidence_inventory`. |
| `command_to_reproduce` | How a human re-derives this one finding: a shell command or a plain-language instruction. Free text; not tested for conformance. MAY be `null` when no meaningful instruction exists; MUST NOT be an empty string. |
| `grounded_in` | Comma-separated standard IDs from §9.1. Every finding MUST cite at least one. |
| `validation_mode`, `mode_verdict`, `method_badge` | Present on mode-keyed findings, i.e. every per-validator `claim_validators/<cid>.<vid>` finding (including resolution errors, which carry `unverifiable`), `claim_validators/skeleton`, and the claim-level `claim_validators/<cid>` finding of a non-hypothesis claim with no validator (§4.5.2 rule 3: `mode_verdict: "unverifiable"`, `validation_mode: null`, `method_badge: null`); `null` otherwise. Hypothesis findings (rule 2) have `mode_verdict: null`. `validation_mode` is the validator's declared mode, else its Result's `validation_mode`, else derived from the validator kind (`builtin` → `re-analyze`, `procedure` → `re-execute`, `llm_judge` → `inspect`, `attest` → `attest`). `method_badge` is the **per-finding** badge: `inspected` for `evidence-supported`, `attested` for `attested`, `re-executed`, `from released data` for `re-analyzed`, else `null`. The run-level method badge is separate (§4.7). |
| `display_weight` | Optional, display-only ordering hint copied from producer metadata. MUST NOT feed aggregation. |
| `display` | Free-form presentation hints. MUST NOT feed aggregation. |

## 4.3 Evidence-conditioned activation

Each check names the evidence it needs, keyed on the manifest's evidence inventory and the
presence of index files. Apply invariant I5 uniformly:

| Situation | Result |
|-----------|--------|
| Evidence never declared (flag false/absent, index file absent) | `unassessable`, with a message naming what was missing. |
| Evidence declared but the pointer does not resolve (missing file, unknown ID, unsafe path, empty file) | `unverifiable`, with the word "integrity" in the message. |
| Inventory flag contradicts the index (e.g. `has_traces: true` but zero traces resolve) | `unverifiable` (declared-but-unresolved). |

## 4.4 Check order

Checks run in this fixed order (trust order: structure first, interpretation last). Each check
is `artifact → list of findings`; a check MUST NOT read another check's findings.

1. `structure`
2. `claim_validators`
3. `paper_consistency`
4. `provenance`
5. `assessments`
6. `reproduce` (only when reproduction is requested, §4.9)

An exception inside a check MUST be caught and turned into one `unverifiable` finding
(`<check>/error`) plus a warning. It MUST NOT abort the run. The error finding uses the check's
own `grounded_in` IDs and keeps any findings the check emitted before the exception.

**Finding order** is part of the output contract (needed for J28): checks in the order above;
within a check, the order given in its section below. Where a section says "per X in declared
order", findings follow the declaration order in the index file.

## 4.5 Checks

Each check below lists its finding IDs, conditions, and verdicts. `grounded_in` values refer to
§9.1.

### 4.5.1 `structure` (S1, S3)

| Finding ID | Condition → verdict |
|------------|---------------------|
| `structure/readme` | A root `README*` exists → `verified`. None exists → `unassessable` (the SDK does not require one). |
| `structure/paper` | `paper.pdf` or `paper.source` resolves → `verified`. Paper object declared but nothing resolves → `unverifiable`. No paper object → `unassessable`. |
| `structure/dependencies` | An image is **declared** (§2.3.1: `environment.image.reference` is a non-empty string) → `verified`. Otherwise → `unverifiable` ("environment not declared; reproduction cannot be provisioned"). |
| `structure/environment_pinned` | Only when an image is declared. **Pinned** per §2.3.1 (`image.digest` matches `^sha256:[0-9a-f]{64}$`, or `image.reference` embeds `@sha256:<64 hex>`) → `verified`. Otherwise (a bare tag, or a malformed digest) → `advisory` (mutable; risk of drift). |
| `structure/experiments` | ≥1 experiment with a non-empty `run.command` → `verified`. Otherwise, if the inventory says `has_runnable_experiments: true` → `failed`. Otherwise → `unassessable`. |
| `structure/experiments-runnable` | For each experiment, split `run.command` on whitespace (no shell parsing). Skip tokens starting with `-` and tokens containing `=`, `$`, or `://`. A remaining token is path-like if it contains `/` or ends in `.<1–5 alphanumerics>`. Resolve it against the artifact root, then against the experiment's `directory`; it is missing if neither exists. If any are missing → one `unassessable` finding listing them (they may be created at run time or live in the image). If none are missing → no finding. |

Order: the rows of this table, top to bottom.

### 4.5.2 `claim_validators` (S1, S3, S7)

Run per claim in `claims.yml`, in declared order. If no claims index is declared, emit one
`claim_validators/none` finding, `unassessable` ("no claims declared"), and nothing else. If it
is declared but does not resolve (§2.3.1), emit one `claim_validators/none`, `unverifiable`
(integrity; message MUST contain "does not resolve"), and nothing else.

For each claim, apply the first rule that matches:

1. **Placeholder claims** (no statement and no validators) are collected and reported together
   as one `claim_validators/skeleton` finding, `unverifiable`, listing their IDs. This finding is
   emitted **after** all per-claim findings.
2. **Hypotheses** (`stance: hypothesis`) are not judged for substantiation. Emit
   `claim_validators/<cid>` as `advisory` ("hypothesis; held to honest testing, not
   substantiation"), with no mode verdict. For each `tested_by` experiment whose
   `disposition.status` is `failed` or `abandoned`, emit an additional `advisory` finding
   `claim_validators/<cid>/negative-result/<slug>` (`<slug>` is the experiment slug) recognizing a
   **preserved negative result**, quoting the disposition rationale. A hypothesis MUST NOT yield
   `failed` or `unverifiable`.
3. **Findings with no validators** (no `validators`/`validator` field, or an empty list) →
   `claim_validators/<cid>`, `unverifiable`, `mode_verdict: "unverifiable"`,
   `validation_mode: null` ("no validator declared; cannot be settled"). A Result that
   `validates` the claim is shown as evidence on the finding but does not substitute for a
   validator. (Paper-origin claims always carry one `attest` validator, §3.5, so they are
   evaluated under rule 4, not here.)
4. **Otherwise** evaluate each validator `v` (ID `claim_validators/<cid>.<vid>`, where `vid` is
   the validator's `id`, or `v<i>` with `i` its **0-based position in the declared list**).
   Evaluate **gates first**: an `attest` validator is a *gate* iff another validator on the same
   claim names it in `gated_by`. Emit findings in evaluation order: gates in declared order,
   then the remaining validators in declared order.

| Validator kind | Behavior |
|----------------|----------|
| `builtin` | Resolve `input.result` to a declared Result. Unknown ID → `unverifiable` (integrity: declared-but-unresolved). No input → `unverifiable`. Resolve the operand (§4.6). On resolution error → `unverifiable` (integrity). Run the catalog function: pass → `verified` / `evidence-supported` / badge `inspected`; fail → `failed` / `failed`; cannot decide → `unverifiable` / `unverifiable`. When run by the reproduction provider against regenerated outputs, a pass is `re-executed` or `re-analyzed` instead (§4.9). |
| `attest` as gate | Run the attest check (below). Emit `advisory` with no mode verdict, stating "gate passed" or "gate failed". Remember the outcome. |
| `attest` as the claim's own validator | Pass → `advisory` with mode verdict `attested`, badge `attested`. Fail → `unverifiable` / `unverifiable` (integrity; never a silent pass). |
| `llm_judge` (inspect) | No `gated_by` field (or an empty one) → `advisory`, mode `inspect`, no mode verdict ("ungated inspection"; it cannot reach `evidence-supported` without a passing gate, SDK §3.4). `gated_by` present but its gate failed, or `gated_by` names no `attest` validator on the same claim → `unverifiable` / `unverifiable` ("blocked by attest gate"). Gate passed → `advisory`, mode `inspect`, no mode verdict. An optional LLM pass MAY annotate it (§4.10) but MUST NOT set a verdict. |
| `procedure` | Without a reproduction provider → `unverifiable` / `unverifiable` ("declared, run-to-verify"). With one, the provider runs the procedure; the external tool's deterministic outcome gives `re-executed` (success) or `failed`. |
| missing or unknown `kind` | `unverifiable` / `unverifiable` ("unknown validator kind"). |

**Attest checks** (`checks` field):

| `checks` | Passes when |
|----------|-------------|
| `provenance`, `integrity` | `inputs` is non-empty and every input Result is declared and its `evidence` resolves to a non-empty file. |
| `ethics` | Some dataset carries a non-empty `study` block. (Absence fails the attest but is described as advisory.) |
| `citations_exist` | A references export resolves and lists ≥1 reference. |
| other | Never passes ("unknown attest kind"). |

### 4.5.3 `paper_consistency` (S3, S6) — advisory

Do the paper's reported numbers appear in the artifact's shipped evidence?

Every finding of this check is `advisory`, except the `unassessable` case.

| Situation | Finding |
|-----------|---------|
| No paper | `paper_consistency/none` ("not applicable"). |
| Paper text cannot be extracted | `paper_consistency/unreadable`. |
| No result-shaped numbers found | `paper_consistency/no-numbers`. |
| Numbers found but no shipped CSV/TSV/JSON/Markdown evidence | `paper_consistency/unassessable` (`unassessable`). |

Otherwise:

1. **Harvest** result-shaped numbers from the paper exactly as in §3.4 steps 0–3 (same
   page-furniture removal, segmentation, token classes, skip rules, and dedup key). Bare integers, defined on the
   source token (§3.4), are excluded. Record each number's raw token, page, section, and
   sentence; the sentence is a normalized excerpt (§2.8).
   Section headings and section labels are those of §2.7 (Markdown or LaTeX headings, numbered
   headings with a title phrase such as `2.4 Cross-Domain Robustness Analysis` or
   `5 DISCUSSION`, and named headings), so the judge and the adapter label every number alike.
   A number is **headline** if its section is the abstract, introduction, contributions, or
   conclusion, or its sentence cites a figure or table (`Fig.`, `Figure`, `Table`).
   **Salience** = 2 if headline, plus 1 if the sentence contains result language (`achieve`,
   `improve`, `outperform`, `reduce`, `increase`, `accuracy`, `speedup`, `error`); ties are
   broken by position in the paper (earlier first).
   *Conformance tests only use fixtures where these rules are unambiguous; implementations MAY
   use better heuristics if they still satisfy every L1 scenario.*
2. **Collect values** from **shipped evidence**, meaning the files named by the `evidence` field
   of declared Results (nothing else), **excluding** any Result whose `evidence` path equals the
   manifest's declared paper file (`paper.pdf` or `paper.source`, compared as written after
   removing a leading `./`). A paper is not evidence for its own numbers. A paper-origin
   artifact (§3.4, every Result points at the paper) therefore has no shipped evidence and
   yields `paper_consistency/unassessable`. Numeric cells
   (CSV/TSV), numeric leaves (JSON), and numeric tokens (Markdown) count. Skip files over a size
   budget (reference value: 5 MB). Stop after a value budget (reference value: 200,000 values)
   and warn.
3. **Match** precision-aware: a reported number with *d* decimals matches a shipped value within
   half a unit in the last place, `0.5 × 10^-d`, with a floor of 1e-9. A percentage also matches
   its fraction form (value / 100) at two more decimals of precision.
4. **Emit**, in this order:
   - `paper_consistency/summary`: counts of harvested, corroborated, and unmatched numbers, and
     corroborated/total for headline numbers. MUST contain "advisory cross-check, not a verdict".
   - `paper_consistency/claim/<n>`: up to 12 headline sentences, deduplicated by whitespace-
     collapsed lowercase text, highest salience first. `<n>` is 1, 2, 3, … in emitted order.
     Each is marked corroborated only if **every** number in it matched, and quotes the
     (normalized, §2.8) sentence with page and section.
   - `paper_consistency/unmatched/<raw>`: up to 10 non-headline unmatched numbers, highest
     salience first, each with its quote. `<raw>` is the number's text as written with
     whitespace removed and every character outside `[A-Za-z0-9.%-]` replaced by `_`. Numbers
     with the same `<raw>` are reported once (the most salient).
   - `paper_consistency/unmapped-claims`: `advisory` (presentation role `coverage`), when the
     paper has numbers but no claim declares a numeric validator (`numeric_close`,
     `numeric_threshold`, `monotonic`), noting that the claim → evidence map is unfilled.

Unmatched numbers are prompts for a human, not failures.

### 4.5.4 `provenance` (S1, S3)

Integrity of shipped bytes. **Integrity is not authenticity** and every message MUST say so
where relevant.

| Finding ID | Condition → verdict |
|------------|---------------------|
| `provenance/checksums` | No `SHA256SUMS` → `unassessable`. Unreadable, a symlink, or larger than a declaration budget (reference value: 2 MB) → `unverifiable`. Empty → `unverifiable`. Emitted only in these cases; a readable, non-empty file produces only per-line findings. |
| `provenance/checksums/<line>` | One per non-blank line, in file order. `<line>` is the **1-based physical line number** in the file (blank lines are counted but produce no finding); evidence anchor `SHA256SUMS#L<line>`. The line must match `^[0-9a-fA-F]{64} [ *](.+)$`: the standard `<hex>␣␣<path>` (text) or `<hex>␣*<path>` (binary) form. A single space between hash and path is **malformed**. Malformed; unsafe, duplicate, or self-referential path; missing; symlink; or over budget (reference values: 100 MB per file, 1 GB total) → `unverifiable`. Hash equal → `verified`. Hash different → `unverifiable`; message MUST contain "not proof of misconduct". |

**Duplicate and self-referential paths.** A path is a **duplicate** when its text, exactly as
written after the separator, equals the path of an earlier line (no normalization: `a.txt` and
`./a.txt` are different texts, and `./a.txt` is unsafe anyway, §2.4). The **first** line naming a
path is evaluated normally; every later line naming the same path is `unverifiable` (message
names the earlier line). A line naming `SHA256SUMS` itself is self-referential → `unverifiable`.
Duplicates do not invalidate the first line's verdict.

A checksum mismatch MUST NOT produce `failed`. Provenance findings do not drive the rubric
(§4.7) but are shown in all reports.

### 4.5.5 `assessments` (S1, S3, S4, S7) — advisory

Artifact-level dimensions. **Every** finding here is `advisory`, `unverifiable`, or
`unassessable` and none has a mode verdict. A producer-declared entry in `assessments.yml` for
the same `dimension` is honored as an annotation: the message is suffixed with
"(producer annotation `<entry id>` honored)".

**IDs and order.** Dimensions are evaluated in table order. Each emits `assessments/<dimension>`;
sub-findings are `assessments/<dimension>/<sub>`. Per-trace findings of
`trace_report_faithfulness` are `assessments/trace_report_faithfulness/<trace id>`, in declared
order; there is no summary finding when per-trace findings exist.

**Trace fields used:** `id`, `kind`, `path`, `terminal_state`. A trace without `terminal_state`
is treated as declaring `unknown`.

| Dimension | Needs | Behavior |
|-----------|-------|----------|
| `execution_authenticity` | traces | No traces → `unassessable`. Inventory says traces but none resolve → `unverifiable`. Exclude `human_interaction` traces; none left → `unassessable`. Otherwise `advisory`, counting traces whose declared `terminal_state` is `completed_with_outputs` against those `planning_only`, `debugging_no_run`, `aborted`, or `unknown`. Always emit two process-transparency sub-findings after the main finding, whatever its verdict (including `unassessable`): `…/experiment_funnel` (attempted → reported counts from dispositions and the inventory's `experiments_attempted`/`experiments_reported`; missing rationales noted; no experiments and no counts → `unassessable`) and `…/provenance_journal` (journal absent → `unassessable`; else entry count and how many carry a rationale). |
| `trace_report_faithfulness` | traces with readable bodies | For each run trace (excluding `human_interaction`), re-derive the terminal state (below). Body missing, unreadable, or over budget (reference value: 5 MB) → `unverifiable` for that trace. Re-derived or declared state `unknown` → `unverifiable` ("ambiguous"). Disagreement → `unverifiable`; message MUST contain "flagged for a human". Agreement → `advisory` for that trace. No run traces → a single `assessments/trace_report_faithfulness`, `unassessable`. |
| `citation_integrity` | references export | Absent → `unassessable`. Declared but unreadable → `unverifiable`. Otherwise report how many references carry an existence-checkable identifier (DOI, arXiv ID, ISBN, URL): some → `advisory`; none → `unverifiable`. |
| `related_work_validity` | paper text with a related-work section (or a related-work export) | Absent → `unassessable`. Otherwise extract positioning statements and count: total, with a citation, comparative, and **superiority** claims ("outperforms", "first to", "state-of-the-art", …). Superiority claims without a citation → `unverifiable` (concern for a human); otherwise `advisory`. |
| `limitation_transparency` | `reflection.md` | Absent → `unassessable`. Present but without limitation signals ("limitation", "threat to validity", "does not", "fails to", "future work", …) or only template text → `unverifiable`. Otherwise `advisory`. |
| `agent_faithfulness` | `research_agent` in the manifest (§2.3.1) | Absent → `unassessable`. File at `research_agent.path` missing, no pinned `model`, or a `grounding_sources` entry that does not resolve → `unverifiable`. Otherwise `advisory`. A deeper probe of the agent is an LLM extension and MUST stay advisory. |

**Terminal-state re-derivation.** The trace body is opaque. Interpret only this optional,
neutral shape: a JSON array, an object `{"events": [...]}`, or JSON Lines, where events with
`role` ∈ {`executor`, `tool`} and `type: "run_end"` carry `status`, an integer `exit_code`, and
`outputs` (a list of non-empty strings). `run_id` on an event is optional; if the matching
events carry two or more distinct non-null `run_id` values, or there are no matching events →
`unknown`. Using the last matching event: `status: aborted` with non-zero code → `aborted`;
`status: completed`, code 0, non-empty `outputs` → `completed_with_outputs`; otherwise
`unknown`. Never parse provider-specific transcript formats.

**Parsing precedence** (decides between JSON and JSON Lines, so a one-line JSON Lines file is
never misread as a single JSON document):

1. If the trace `path` ends in `.jsonl` or `.ndjson` (case-insensitive), parse as **JSON Lines**:
   every non-blank line is one JSON value, and the events are those values in line order. Any
   line that is not valid JSON, or any value that is not an object → `unknown`.
2. Otherwise parse the whole body as one JSON document. An array is the event list; an object
   with an `events` array uses that array; any other object or scalar → `unknown`.
3. Otherwise (the body is not one valid JSON document), parse as JSON Lines as in step 1.

After parsing, events that are not objects make the trace `unknown`.

### 4.5.6 `reproduce` (S1, S2)

Only when reproduction is requested. Precedence:

1. If the manifest's `origin.evidence_cap` is `attested` (a paper-origin artifact, §3.3), emit
   exactly one `reproduce/deferred`: `unassessable`; message MUST contain "evidence_cap". The
   `reproduction` stage is `not-run`. No provider is called.
2. Otherwise, without a reproduction provider, emit exactly one `reproduce/deferred`:
   `unverifiable`, "reproduction requested but no reproduction provider is configured". The
   `reproduction` stage is `unavailable`. With a provider, see §4.9. When reproduction is not requested, emit nothing; the run
manifest's `reproduction` stage records `not-requested` (§6.4).

### 4.5.7 Contribution diagnostics (structural, outside the rubric)

When the artifact declares contributions (v3, §2.3.1), the judge validates the declarations
**structurally**. It never assesses whether a contribution is significant, original, or
supported; that is the reviewer's advisory work (§5.13) and, finally, a human's.

Diagnostics are **not findings**. They are a separate list, `contribution_diagnostics` in the
judge result (§6.6), and therefore never enter aggregation (§4.7), the badge profile (§4.8), the
presentation roles, or the exit status (§6.8). They are computed for every artifact-informed run
and are independent of whether reproduction is requested. A v2 artifact, or a v3 artifact
without `paths.contributions`, has an empty list.

Each diagnostic is `{path, message, severity}`: `path` is a dotted/indexed location
(`contributions[2].supporting_claims`, `paths.contributions`), `severity` is `error` or
`warning`. The list is ordered by contribution index, then by the order of the rules below. A
conforming tool MUST produce at least these diagnostics (message wording is free; the
quoted phrases are reference wording):

| Rule | `path` | Severity |
|------|--------|----------|
| Loading failures (§2.3.1 table) | `paths.contributions` or `contributions[i]` | error |
| `id` or `statement` missing, not a string, or whitespace-only ("required nonempty string") | `…[i].id` / `…[i].statement` | error |
| `id` equal to an earlier contribution's `id` ("duplicate contribution ID") | `…[i].id` | error |
| The self-qualification field `established` is present at the top level of a contribution, whatever its value ("qualification belongs to a separate human assessment"). This is the complete self-qualification set; any other unknown field is open and not diagnosed (last row). | `…[i].established` | error |
| `type` present but not a string | `…[i].type` | error |
| `supporting_claims` not a list of unique non-empty strings | `…[i].supporting_claims` | error |
| A `supporting_claims` entry names no declared claim ("unresolved supporting claim") | `…[i].supporting_claims` | error |
| `supporting_claims` absent or empty ("claim support not declared") | `…[i].supporting_claims` | **warning** (a legal draft) |
| A locator (`paper_ref`, comparison `locator`, provenance `locator`) is not a mapping, has a `page` that is neither a number nor a string, a `char_start`/`char_end` that is not a non-negative integer, or `char_end < char_start` | the locator path | error |
| `significance.impact` not `anticipated` or `observed` | `…[i].significance.impact` | error |
| An `evidence` citation is not `claim:ID`, `result:ID`, `reference:ID`, or `paper:<locator>` ("unsupported evidence citation"), or names an undeclared claim/result ("unresolved evidence citation") | the `evidence` path | error |
| A `reference:ID` citation whose `ID` is not in the references export ("unresolved evidence citation") | the `evidence` path | error when the export resolves; **warning** when no references export resolves (same rule as comparison references, below) |
| An `originality.comparisons[j]` lacks a non-empty `reference` or `distinction` | `…comparisons[j].reference` / `.distinction` | error |
| A comparison `reference` is not an `id` in the references export ("unresolved prior-work reference") | `…comparisons[j].reference` | error when the export resolves; **warning** when no references export resolves (identities cannot be checked, SDK §2.4.2) |
| `originality.coverage.sources`/`uninspected` not a list of non-empty strings | that path | error |
| `provenance.kind` not `author-declaration`, `paper-extraction`, or `reviewer-inference` | `…[i].provenance.kind` | error |

Unknown fields are preserved and never diagnosed (SDK §2.4.2 records are open).

## 4.6 Builtin validator catalog

Semantics are fixed so independent implementations agree.

**Operand resolution.** `input` is `{result: <id>, series?: [<locator name>, …]}`. Without
`series`: `output_present` and `contains` use the **whole evidence file** (as text); every other
validator uses the Result's single locator, and a Result with zero or several locators is a
resolution error. With `series`, the operand is the list of values from those named locators,
in order. A series is always a list, even with one name; validators that need a number take the
single element of a one-element list. A locator is one of:

| Locator | Resolves to |
|---------|-------------|
| `{value: x}` | The literal `x`. |
| `{column: c, row: r}` on CSV/TSV | Cell in column `c` of the row selected by `r`: absent, `last`, or `final` → last row; `first` → first row; an integer, **or a string of an optional `-` followed by digits** (e.g. `"0"`, `"-1"`) → that 0-based index (negative counts from the end); any other string → the first row whose `metric`, `name`, or `key` column (first that exists, in that order) equals it, compared trimmed and case-insensitively. |
| `{json_path: "a.b.0.c"}` on JSON | Dotted path; integer segments index lists. |
| `{text: true}` | The whole file decoded as UTF-8. |

Any locator that does not resolve is a resolution error (→ `unverifiable`, integrity), with one
exception: `output_present` never reads a locator and reports a missing or empty declared file
as its own `fail` (table below), because absence is exactly what it tests. Numbers
are parsed as IEEE-754 doubles; a non-numeric value where a number is required →
`unverifiable`.

| Name | Status | Passes when | Params |
|------|--------|-------------|--------|
| `numeric_close` | shipped | `|a − e| ≤ max(rel_tol × max(|a|, |e|), abs_tol)` | `expected`, `rel_tol` (default 0), `abs_tol` (default 0). With both defaults, only exact equality passes. |
| `numeric_threshold` | shipped | `a op bound` | `op` ∈ `>=`, `<=`, `>`, `<`, `==` (default `>=`); `bound`. Bad `op` or operand → `unverifiable`. |
| `monotonic` | shipped | Series of ≥2 numbers is non-strictly increasing or decreasing at every step | `direction` ∈ `increasing` (default), `decreasing`; other → `unverifiable`. A scalar or a series of fewer than 2 points → `unverifiable`. |
| `exact_match` | shipped | `trim(str(a)) == trim(str(expected))` | `expected` |
| `contains` | shipped | Text contains `expected` as a substring, or a list contains it as an element | `expected` |
| `output_present` | shipped | The Result's evidence exists, is a regular file, and is non-empty. A declared `evidence` path that is missing, not a regular file, or zero bytes → `fail` (mode verdict `failed`); a Result that declares no `evidence` at all → `unverifiable` (a resolution error). | — |
| `set_ranking` | staged | `mode: set` → same elements (compared as strings); `mode: order` → identical sequence | `expected`, `mode` (default `set`) |
| `distribution_close` | staged | Always `unverifiable` in v1 (no statistical test defined yet) | `test`, `alpha` |
| unknown name | — | Always `unverifiable` | — |

Implementations MAY add validators, but an added name MUST NOT change the meaning of a name in
this table (§7.5).

## 4.7 Aggregation into the rubric

Inputs: all findings. Output: `REPRODUCED`, `PARTIAL`, or `NOT_REPRODUCED`.

```text
relevant(f)  = (f.mode_verdict != null) or
               (f.check in {structure, reproduce} and f.verdict != advisory)
failure(f)   = f.mode_verdict == failed      if f.mode_verdict != null
               f.verdict == failed            otherwise
unassess(f)  = f.mode_verdict == unassessable if f.mode_verdict != null
               f.verdict == unassessable      otherwise
REPRO        = {re-executed, re-analyzed}

R = [f in findings where relevant(f)]
if any(failure(f) for f in R):                      return NOT_REPRODUCED
reproduced_ok = any(f.check == reproduce and f.verdict == verified)
T = [f in R where not unassess(f) and
                  (f.mode_verdict != null or f.check == reproduce)]
strong(f) = f.mode_verdict in REPRO                 if f.mode_verdict != null
            reproduced_ok and f.verdict == verified otherwise
if (reproduced_ok or any(f.mode_verdict in REPRO for f in T))
   and T is non-empty and all(strong(f) for f in T): return REPRODUCED
return PARTIAL
```

Consequences a conformance suite checks (§8):

- `structure` failures block everything; `structure` successes do not count toward
  `REPRODUCED`.
- `provenance`, `paper_consistency`, `assessments`, and `advisory` findings **without a mode
  verdict** never move the rubric.
- A claim settled by attestation (`attested`) or inspection (`evidence-supported`) caps the run
  at `PARTIAL`, even if every other claim was reproduced. This is intended: such a claim was not
  independently reproduced.
- Without a reproduction provider, no finding can be `re-executed` or `re-analyzed`, so the
  rubric is at most `PARTIAL` (I7).
- `unassessable` findings never lower the rubric.

Contribution diagnostics (§4.5.7) are not findings and never move the rubric.

**Run-level method badge** (the judge result's `method_badge`; set **only** when the rubric is
`REPRODUCED`, otherwise `null`): `re-executed` if a `reproduce` finding is `verified` or any
mode verdict is `re-executed`; otherwise `from released data`. Per-finding badges (§4.2) are
set as defined there and are independent of the rubric.

**Relation to the SDK's worked example.** The SDK's Appendix A says a deterministic builtin over
shipped evidence yields `re-analyzed`, and that an inspect validator can reach
`evidence-supported`. This specification is deliberately stricter (I7, I8): the tool did not
re-analyze anything itself, so the result is `evidence-supported`, and model-based inspection is
advisory. A tool conforming to this specification follows §4.1 and §4.5.2.

## 4.8 Badge profile (ACM-compatible, S1)

Badges are a **profile** layered on the rubric. They are computed, displayed, and never feed
back into the rubric. They are serialized in the judge result (§6.6) as an object with exactly
these keys, each holding exactly one of the status values `awarded`, `unverifiable`,
`not_awarded`:

```json
"badges": { "available": "awarded", "functional": "unverifiable", "results_reproduced": "unverifiable" }
```

| Badge | Rule |
|-------|------|
| **Available** (`available`) | A root license file (`LICENSE`, `LICENSE.*`, `COPYING`) **and** a paper that resolves → `awarded`. Paper resolves but no license → `unverifiable` (license absence is advisory). No paper → `not_awarded`. |
| **Functional** (`functional`) | Any `structure` finding `failed` → `not_awarded`. Otherwise, `structure/dependencies` `verified` **and** `structure/experiments` `verified` → `awarded`. Otherwise `unverifiable`. |
| **Results Reproduced** (`results_reproduced`) | `REPRODUCED` → `awarded`; `PARTIAL` → `unverifiable`; `NOT_REPRODUCED` → `not_awarded`. |

ACM's "Reusable" badge requires human judgment and is out of scope; no `reusable` key is
emitted. Contribution diagnostics never affect any badge.

## 4.9 Reproduction hook

Reproduction is an extension point (§7.2). The judge's obligations around it:

1. Reproduction runs only when requested **and** a provider is configured.
2. The provider receives a read-only snapshot path, the experiment declarations, the environment
   declaration, datasets, and a policy (time and resource budgets, network allowed or not).
3. Regenerated outputs MUST be written under `<run>/reproduction/<slug>/`. They MUST NOT
   overwrite any snapshot file.
4. For each claim whose builtin validators read a Result `produced_by` a re-run experiment, the
   judge re-runs those validators with evidence paths remapped to the regenerated outputs. Pass
   → mode verdict `re-executed` (or `re-analyzed` if the provider re-ran only the analysis over
   released data). Fail → `failed`. Missing regenerated output → `unverifiable`.
5. Every **repair** the provider had to make to get an experiment to run (a changed file, a
   pinned seed, a patched path) MUST be recorded as a unified diff under
   `<run>/reproduction/<slug>/repairs/` and reported as an `advisory` finding
   `reproduce/<slug>/repair/<n>`. Repairs are reproducibility findings in their own right.
6. Per-experiment execution records (command, exit code, duration, environment identity,
   stdout/stderr paths) are written to `<run>/reproduction/<slug>/execution.json` and summarized
   as `reproduce/<slug>`: success → `verified`; non-zero exit → `failed`; timeout, budget
   exhaustion, or could not start (image unavailable, credential-gated data) → `unverifiable`
   (running out of budget is not evidence against the claim).

## 4.10 Advisory overlays

Overlays add information next to the deterministic result. They MUST NOT change any finding's
verdict, the rubric, or the badges (I2, I12).

**Reference existence check.** For each reference (from the references export, or extracted from
the paper), ask the reference resolver (§7.3) whether it exists. Per-reference status:
`verified` (found, with matching title/authors), `unverified` (not found, or found with
mismatched metadata), `error` (lookup failed), `unchecked` (not attempted; for example over
budget). Store the summary in the judge result's `reference_check` (§6.6). Resolver failure →
all `unchecked` plus a warning.

**LLM claim extraction** (requires an LLM provider, §7.1):

1. An **extractor** reads the paper and proposes result claims, each with an exact quote.
2. An independent **verifier** (separate call, MAY be a different model) sees only the paper and
   one proposal, and accepts or rejects it with a reason.
3. An optional **substantiator** searches the paper's results section for the support of each
   accepted claim and records a quote, or `unverifiable`.
4. Quotes MUST be located in the paper text with the *squash* procedure (§2.8). Proposals whose
   quote cannot be located are dropped.
5. Output: `extracted-claims.json` and `extracted-claims.md` in the run directory, each marked
   generated and labeled advisory.
